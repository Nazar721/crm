### Синтетичні сценарії, додані/оновлені цією ревізією

`tests/stage1-review.test.ts` (16), `tests/storage-corruption.test.ts` (оновлено 2):

1. невдала міграція не позначається виконаною, блокує редагування, повторний запуск доводить справу;
2. збій запису налаштувань під час імпорту → відновлюється **все**: колекції, налаштування, прапорці;
3. збій фіналізації (міграції) після запису колекцій → та сама повна звірка;
4. відмова відновлення → `recovered:false` + явний блок запису;
5. міграції **не** перезаписують пошкоджену колекцію порожнім масивом;
6. непридатний карантин → повідомлення не бреше про збереження оригіналу;
7. заповнене сховище → читання та експорт працюють, запис заблоковано з поясненням;
8. дублікати ID всередині колекції → імпорт відхилено з точною адресою;
9. дублікати ID між активними й завершеними проєктами → відмова;
10. стара комісія (сума) приймається і нормалізується **до** міграції;
11. невизначена одиниця комісії → запис позначається; у строгому режимі → відмова;
12. строгий режим відхиляє імпорт із будь-якою помилкою запису;
13. час останньої повної копії переживає перезапуск;
14. відкладена копія виконується після перезапуску **без нових змін даних**;
15. пригнічення резервування не «застрягає» після невдалого імпорту;
16. експорт додає `issues` (проблеми сховища) і лишається валідним для повторного імпорту.

## 2. Контракти

### 2.1 Сховище — `lib/datasource/types.ts`

```ts
interface CrmDataSource {
  readonly kind: 'local' | 'remote';
  load(): Promise<{ data: DataSnapshot; issues: StorageIssue[] }>;
  writeBlockedReason(): string | null;              // читання працює, запис — ні
  saveCollection(key, value): Promise<WriteOutcome>;
  saveSettings(settings): Promise<WriteOutcome>;
  saveMeta(patch): Promise<WriteOutcome>;
  saveBackupCopy(serialized): Promise<WriteOutcome>;
  listIssues(): StorageIssue[];
  clearIssues(): void;
  clearCollectionIssue(collection): void;           // після успішного відновлення
}
```

**Скоупи запису** (`lib/store.ts`):

| Скоуп | Хто | Що блокує |
|---|---|---|
| `user` | доменні дії (форми/AI) | пошкоджена колекція, заблокований запис сховища, незавершені міграції |
| `system` | міграції | пошкоджена колекція, заблокований запис сховища |
| `import` | імпорт/відновлення | нічого логічного — лише реальні помилки вводу-виводу |

**Гарантії локального адаптера (і межі):**
- `load()` не кидає виняток на непридатному JSON: сирий вміст ізольовується в
  `crm_corrupt_<key>`, фіксується issue з колекцією, колекція позначається пошкодженою;
- `load()` не кидає виняток, якщо сховище читається, але не пишеться (ліміт):
  такий стан оголошується через `writeBlockedReason()`;
- `load()` кидає виняток **лише** коли читання неможливе (тоді — стан `error`);
- `saveCollection()` **НЕ атомарний** щодо інших колекцій;
- **не гарантується локально**: атомарність, ідемпотентність, захист від паралельних
  змін (дві вкладки), версіонування рядків. Це фіналізує **етап 2 на сервері**.

**Життєвий цикл сторінки:** `idle → loading → (ready | error)`; дані стають доступними
лише після `initStore()` → `runMigrations()` → `reloadStore()`.

### 2.3 Запис, версія, повний експорт — `lib/export.ts`

```ts
EXPORT_FORMAT_ID     = 'WebAgency CRM'
EXPORT_SCHEMA_VERSION = 2          // старі файли мали version: 1
```

`buildExportPayload(snapshot)` → `app`, `version`, `exportedAt`,
`data` (усі 8 колекцій **повністю**, незалежно від пагінації/фільтрів),
`financeSettings`, `meta`, **`issues`** (проблеми сховища, напр. пошкоджені колекції).
Секрети виключаються `stripSecrets()` за назвою поля на будь-якій вкладеності.

**Прийом файлів** (`lib/validate-backup.ts`, `validateBackup(raw, { strict? })`):
- `version > 2` → відмова; `version 1/2` з `data` → основний формат;
- `legacy-flat` → **явно визначений** старий формат (окреме попередження);
- усе інше → «Невідомий формат файлу», жодного запису;
- обов'язкові масиви; **унікальність ID** у колекції та між активними/завершеними проєктами;
- **комісія партнеру** нормалізується (сума → відсоток, ідентично `v16`) до остаточної
  валідації; невизначна одиниця → помилка запису;
- невалідний запис → пропускається з явною помилкою (не у `strict`);
- **`strict: true`** → будь-яка помилка запису блокує імпорт (для фінальної міграції етапу 2).

**Імпорт** (`lib/importer.ts`):
`previewImport(raw, {strict?})` → нічого не пише;
`applyImport(raw, {strict?})` → `ImportReport { ok, stage, written, recovered?, restoreSkipped?, issue?, errors }`,
`stage ∈ validate | safety-copy | write | settings | finalize | done`.
Порядок: валідація → копія попереднього стану → колекції → налаштування → міграції.
**Будь-яка відмова після копії** → єдина процедура відновлення (колекції + налаштування +
мета + **прапорці міграцій**), виконана всередині `withBackupsSuppressed`.
Колекції, що були пошкоджені до імпорту, **не перезаписуються** (у пам'яті там `[]`,
оригінал лише в карантині) — їх повертається в `restoreSkipped`.

**Міграції** (`lib/migrations.ts`):
`migrate(): { applied, skipped, failed }` — прапорець ставиться лише після успіху,
після першої відмови ланцюжок зупиняється. `runMigrations()` додатково виставляє/знімає
блок запису в `store`.

### 2.4 AI-транспорт — `lib/assistant/contract.ts`

```ts
interface AssistantTransport {
  readonly id: 'not-connected' | 'demo';
  send(req, signal?): Promise<AssistantReply>;
  clarify(req, signal?): Promise<AssistantReply>;
  confirm(req, signal?): Promise<AssistantConfirmResult>;
  cancel(requestId): void;
}
type AssistantReply =
  | { kind: 'text'; text } | { kind: 'draft'; draft }
  | { kind: 'clarify'; text; questions } | { kind: 'error'; error };
type AssistantConfirmResult =
  | { kind: 'applied'; domain; recordId; route?; summary }
  | { kind: 'demo'; domain; summary }          // жодного запису
  | { kind: 'error'; error };
type AssistantErrorCode =
  'not_connected' | 'invalid_key' | 'quota_exceeded' | 'insufficient_credits'
  | 'timeout' | 'model_incompatible' | 'unavailable' | 'cancelled'
  | 'invalid_response' | 'demo_only';
```

`ProviderSettings { provider, model, baseUrl?, demo }` → `crm_assistant_provider`.
`ProviderKeyInput` передається **лише в пам'яті**; `checkKeyFormat()` — локальна перевірка
формату з фіктивним значенням (`persisted: false` завжди). Запису ключа в
`localStorage`/`sessionStorage`/URL/логи/backup **немає** (тест + перевірка в браузері).

### 2.5 Голос — `hooks/useVoiceInput.ts`

`VoiceStatus = idle | unsupported | requesting | recording | processing | ready | denied | error`.
`getUserMedia` + `MediaRecorder` (прослуховування) + Web Speech API (перегляд транскрипції,
якщо браузер підтримує). Відмова доступу → `denied`, відсутність підтримки → `unsupported`.

## 4. Відомі обмеження та рішення для етапу 2

### 4.1 Обмеження, які **не можна** лишити на виробництві
1. **Кілька вкладок.** Store тримає snapshot у пам'яті й **не слухає** подію `storage`:
   запис іншої вкладки може бути витіснений записом цієї (підтверджено синтетично).
   Повідомлення про подію **недостатньо** для одночасних записів — потрібні захист від
   застарілої версії (ETag/версія рядка) і вирішення конфліктів. Це робота етапу 2.
2. **Серверний адаптер не можна підставити під `saveCollection`.** Потрібні операції над
   конкретними записами, транзакції для пов'язаних змін, перевірка версії, права доступу,
   повторні запити без дублів. Заміна цілого масиву на сервері ризикує стерти паралельні зміни.
3. **Атомарність** — localStorage її не має; реальна атомарність/ідемпотентність — етап 2.
4. **Пошкоджений ключ**: розрахунки бачать порожній список, доки користувач не відновить
   імпортом. Запис у таку колекцію заблоковано (не мовчазна підміна), але «порожній»
   вигляд для розрахунків залишається до відновлення.
5. **Важка копія при закритті вкладки** — best-effort; якщо браузер убив вкладку, лишається
   `crm_backup_pending`, і копія робиться при наступному старті (тепер перевірено тестом).
6. **Ключі AI** не зберігаються ніяк — до захищеного серверного secret store (етап 2).

### 4.2 Спірні формули/розбіжності — **не змінював**, потребують згоди на етапі 2
| Місце | Що так як є |
|---|---|
| `dashboardStats.totalBudget` | рахується **лише по завершених** проєктах; `clientDebts`/`specialistDebts` — по **всіх** |
| `project().specialistCost` | `budgetAfterDeductions - projectProfit` |
| `project().receivedProfit` / `paidAmount` | використовуються лише в графіку «Закрито замовлень» |
| Курсова історія | один поточний курс, історичних курсів немає |
| Облік платежів | `incomeStatus: earned | incoming`; транзакції `project_*` не входять у дохід |
| Конвертація | `amount` списується у валюті джерела, `targetAmount` — у валюті призначення |

**Збереження фінансової логіки:** базова формула `project()` не переписана (захищено тестом
«розрахунок проєкту лишається незмінним»). Синтетичні тести **не доводять** повної рівності
реальних даних — перед перенесенням фінальний JSON треба звірити до/після.

### 4.3 Швидкість
Snapshot, індекси, пагінація та винесення важкої копії мають обґрунтований напрямок, але
**числового підтвердження прискорення немає**: потрібен однаковий набір даних і вимірювання
переходів до/після в браузері. Тест пагінації перевіряє обчислення/експорт, **не**
поведінку реального списку та відновлення прокрутки після «Показати ще».

### 4.4 Що етап 2 має реалізувати поверх цього
- Реальний `CrmDataSource` (`kind: 'remote'`): ті самі сигнатури + транзакції, версії,
  ідемпотентність, права доступу, захист від паралельних змін.
- Міграції даних на сервері (локальні `crm_migrated_*` — тимчасові); для фінальної
  міграції використовувати **`strict: true`**.
- AI-ендпоінт, що реалізує `AssistantTransport`; секрети — у серверному `process.env`
  (`.env.example`: `AI_PROVIDER`, `AI_MODEL`, `AI_API_KEY`, `AI_BASE_URL`, `AI_TIMEOUT_MS`
  — **лише назви/пояснення**, значень немає).
- Браузерне приймання (service worker), security-оновлення, реальні API, хостинг.
- Перед перенесенням фінальних даних: база даних, авторизація, тестова міграція з повною
  звіркою, провайдери/секрети/AI-дії й голос, браузерна перевірка, резервування.
