## Що зроблено (усей пакет)

Кнопка «Копіювати» у завершених проєктів (та сама таблиця з `data-label`, усі розміри екранів)
відкриває форму створення (`ProjectForm`, `project=null`) із заповненими умовами. До «Зберегти»
нічого не записується; збереження йде через чинний `saveProject` → новий ID, оригінал у completed
незмінний. AI використовує ту саму логіку через чернетку `projects/create` зі службовим `copyFromId`.

Ця серія завершує виправлення за `REVIEW-PACKAGE-02.md` і `REVIEW-PACKAGE-02-RECHECK.md`:

1. **`handleSave` без undefined `data` і дублікатів.** Побудова payload винесена в чисту
   функцію `buildProjectPayload(values, clients)` (`lib/project-payload.ts`), яку викликає форма
   і яку перевіряють тести — тести бачать саме ті значення, що відправляє форма.
   Джерело `clientId` — тільки поточний `selectedClientId` (`copyPrefill` лише ініціалізує).
   За наявної картки ім'я/telegram/source беруться з неї без `||`-fallback на історичні
   контакти стану (порожнє актуальне значення — теж значення). Відсутність картки в колекції
   НЕ ховається підставою імені: неіснуючий ID відхиляє спільна дія. `savingRef`/`saving`/`finally`
   збережені (повторний клік не дублює, помилка не блокує кнопку).
2. **Валідація clientId у спільній дії та плані.** `_saveProject` приймає явний `clientId` лише
   рядком і лише за наявної картки (невідомий/видалений/неправильного типу → відмова з полем
   `clientId` ДО будь-якого запису); вхідний об'єкт/чернетка НЕ мутується — нормалізується
   окремий `payload`. Наявна картка — джерело істини для `clientName/telegram/source`
   (змішаний стан «ID A, ім'я B» не зберігається), картку клієнта не перезаписуємо.
   `normalizePlan` перевіряє явний `clientId` за `s.clients` для create і update і приводить
   поля чернетки до картки, щоб чернетка показувала рівно те, що збережеться.
3. **AI-копія: явний вибір клієнта.** `clientId` додано до `COPY_CONDITION_FIELDS` — overrides
   копії пропускають новий ID (allowlist не відкидає вибір і не повертає початковий). Порядок
   вирішення: явний `overrides.clientId` (з валідацією) → картка за точним ім'ям в overrides →
   картка джерела; інакше — прапорець `copyClientMissing`.
4. **Видалений клієнт: завершений шлях.** Прапорець зберігається при повторній нормалізації,
   підписанні (envelope) і confirm; знімається лише явним чинним `clientId`. Маршрут повертає
   `clarify` (текст із питаннями тепер потрапляє в історію для моделі) — чернетка не
   створюється, запису нема. Далі за відповіддю власника: (а) чинний клієнт → повторна
   copy-чернетка з `clientId`; (б) явне «створити нового» → окрема підтверджувана
   `clients/create`, потім нова copy-чернетка з її ID. Автоматичного створення картки з
   історичного імені копії більше немає. У формі — той самий явний вибір: новий пропс
   `copyNeedsClientChoice` показує чекбокс згоди; без вибору картки чи згоди «Зберегти»
   не виконується.
5. **AI-update зміни клієнта — явна.** Зміна `clientName` на іншу наявну картку міняє зв'язок
   видимо (`clientId` з'являється в чернетці); назва, що не відповідає жодній картці, при
   наявному зв'язку → зрозуміла відмова з підказкою (явний `clientId` або `clientId: null`);
   `clientId: null` — явне від'єднання з підбором/створенням за ім'ям при збереженні.

## Сценарії (покриті тестами на синтетичних даних, реальними функціями)

1. Копія з чинним перейменованим клієнтом: точний ID, нова картка не створюється, оригінал
   byte-for-byte незмінний (форма, saveProject, AI-шлях).
2. Два клієнти з однаковим ім'ям: зберігається точний ID (не перший збіг за ім'ям).
3. **P1 форми:** вибір B у копії A → у записі B; ручна зміна імені скидає ID (не лишає A);
   видалений ID не ховається fallback на ім'я → відмова.
4. **AI-копія:** явний вибір іншого клієнта (`clientId` у overrides, або точне ім'я) → саме він;
   невідомий `clientId`/назва без картки → відмова або уточнення, не мовчазний початковий ID.
5. `create`/`update` з ghost `clientId`, невірний тип, ID видалений перед збереженням → відмова
   з полем `clientId`; snapshot/clients незмінні; вхідний об'єкт не мутується.
6. Скопійовані історичні контакти не змінюють чинну картку; порожні актуальні контакти
   (`telegram:''`) не відновлюються зі старих значень — ні в картці, ні в новому записі.
7. Видалений клієнт: уточнення до будь-якого запису (чернетка не створюється, commits не
   ростуть); вибір чинного → запис; явне створення картки окремою дією → копія з її ID;
   повторне підтвердження того самого підписаного плану → error, без дублікатів.
8. Повторна нормалізація та confirm-нормалізація підписаного плану не втрачають прапорець
   `copyClientMissing` і повертають уточнення; `copyFromId` не зберігається при
   create/update/null, порожнє значення → явна відмова.
9. Оригінал незмінний; звичайне створення (ім'я → картка) і редагування проєктів не зламані;
   AI-update: інша картка → зв'язок міняється явно; невідома назва → відмова; контакти
   проєкту не розходяться з карткою.

UI-логіку (чекбокс згоди, Autocomplete, подвійний клік) тести не запускають — вона
перевірена статично (typecheck/lint + чиста функція payload, яку викликає сама форма).

## Залишкові обмеження

- Форма: коли картку клієнта вибрано, її ім'я/контакти — джерело істини payload; ручна зміна
  telegram/source при вибраній картці не потрапить у запис (змінюйте контакти на картці
  клієнта). Ручна зміна **імені** від'єднує картку — як і раніше.
- Проєкт із видаленою карткою: оновлення з текстом клієнта вимагає явного `clientId` або
  `clientId: null` (навмисна відмова, не регресія).
- Копіювання досі доступне лише з завершених проєктів; `myPercent` переноситься як умова
  (правила частки не змінювались).
- Прапорець `copyClientMissing` живе тільки в чернетці (не в Project/backup).
