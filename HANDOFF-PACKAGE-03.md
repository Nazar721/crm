## Архітектура (коротко)

Журнал — **окремий шар від DataSnapshot**: він не входить у snapshot, не потрапляє в експорт даних і в AI-контекст як повні дані (лише короткі підсумки). Подія описує **фактичну різницю даних групи**: один commit = одна група = одна кнопка скасування.

- **Remote:** подія створюється **всередині транзакції `crm_commit`** з фактичного diff старого та нового стану колекцій/налаштувань. Успішний commit і журнал атомарні; повтор того самого `request ID` не створює нової події (перевірка `last_request` до diff). **`crm_history_undo(event, request, expected_revision, source)`** (ревізія 2 — **без патча від клієнта**) — окрема серверна транзакція: перевірка власника, **обов'язкова ревізія під `FOR UPDATE`**, ідемпотентність, прив'язана до (запит, подія), і **серверне обчислення інверсії** з `ev.changes` та актуального стану: перевірка «після» для кожної сутності/поля (`CRM_UNDO_CHANGED`), фінальна унікальність ID проєктів (patch vs БД), перевірка залежностей (`CRM_UNDO_DEPENDENCY`), відмова для import/restore/undo/bulk, відновлення лише allowlist-полів налаштувань. Клієнтський engine лишається для попереднього перегляду/повідомлень; сервер йому не довіряє. Стара подія ніколи не видаляється — створюється нова подія-відновлення з позначкою `undone_by`.
- **Local:** після **успіху** доменної дії (`atomicAction`) різниця до/після перетворюється на подію тим самим TS-engine (`lib/history/engine.ts`). Подія пишеться **одним `setItem`** в окремий ключ із **recovery-міткою** `crm_history_pending_v1`: збій запису лишає видимий issue + мітку, наступне читання дописує подію. Атомарності між даними та журналом у localStorage немає — і це задокументовано, не приховано.
- **Скасування:** спільний TS-engine (`computeUndoPlan`) перевіряє поточні значення проти очікуваного «після» події, залежності (клієнт←проєкти, фахівець/партнер←проєкти, проєкт←транзакції), унікальність ID проєктів між активними/завершеними та валідність посилань відновлюваних записів. Група застосовується **атомарно або не застосовується    взагалі**; непов’язані пізніші зміни зберігаються. Повторне скасування тієї самої події → відмова `already_undone`; повтор того самого `request ID` → ідемпотентний успіх без другої події.

## Що зроблено для користувача

- **Налаштування → Історія змін** (нова вкладка): дата/час, розділ, дія, джерело (Форма/Помічник/Імпорт/Система/Застасунок), запис, опис; фільтри за розділом/дією/періодом; пагінація (20/сторінка); розкриття рядка — деталі «було → стало»; кнопка **«Скасувати зміну»** → **попередній перегляд відновлення** (що саме буде відновлено) → явне підтвердження. Після успіху створюється нова подія відновлення (бейдж «скасовано» на старій).
- Події **Імпорт/Відновлення** показуються без кнопки скасування і з посиланням «Відновити з копії» (вкладка «Копії та імпорт»).
- **Експорт/імпорт історії** (окремий JSON, не частина резервної копії даних). Імпортована історія — **окремий недовірий блок лише для перегляду**: без права скасування, з бейджем «імпортована», з вилученням секретів.
- Межа історії в UI: «починається після встановлення пакета; останні 90 днів / до 2000 груп; за межами — скасування недоступне».
- AI: отримує короткі підсумки журналу (`history` у контексті, ≤40 подій), може пояснювати зміни і готувати чернетку скасування (`domain:"history", action:"update", recordId`); маршрут показує попередній перегляд і відмовляє при конфлікті/недоступності. Підтвердження виконується через доменну дію з джерелом «Помічник». Модель не може редагувати журнал і не визначає автора (джерело — лише інформаційний атрибут; власника перевіряє сервер).

## Міграція: `supabase/003-history.sql`

- **Порядок:** `SETUP.sql` (або 001+002) → **`003-history.sql`**. Застосувати **до публікації клієнта пакета 03** (клієнт без міграції працює у деградованому режимі: дані без журналу, вкладка історії показує підказку).
- Старий клієнт **сумісний**: виклики `crm_commit(3 арг.)` ідуть через нову функцію з типовим `p_source = null` → **«Застасунок»**.
- Що створюється: таблиця `crm_history` (RLS увімкнено, **без grant до anon/authenticated** — доступ лише через SECURITY DEFINER функції з перевіркою `auth.uid()`+`crm_owners`); хелпери diff/label/summary/bulk/cleanup/apply (усі з `revoke ... from public, anon, authenticated`); оновлений `crm_commit`; `crm_history_list/get/undo`.
- Обмеження: 90 днів / 2000 подій; очищення **захищає живі recovery-посилання** (подія, на яку посилається утримуване відновлення, не видаляється — пара лишається цілісною; захист має пріоритет над суворим капом).

- **Застереження щодо 001/SETUP:** у репозиторному `001-crm.sql`/`SETUP.sql` у `crm_commit` залишається той самий латентний патерн `jsonb_typeof(e->>'id')` (текст замість JSON-вузла). Файли НЕ змінювалися; `003` замінює `crm_commit` на виправлену версію, тож після 003 дефект усунуто. Задеплоєну функцію варто звірити з репозиторієм (у production коміти працюють — імовірно, задеплоєна версія відрізняється).
- Відкат: `drop function ...; drop table public.crm_history;` — на дані не впливає (крім `crm_commit` — треба повернути 3-аргументну версію з `001-crm.sql`).

## Репродукції для основного агента (контрольована БД)

1. Застосувати `003-history.sql`; перевірити `select proname from pg_proc where pronamespace='public'::regnamespace and proname like 'crm_history%';` (має бути list/get/undo + хелпери) і що `crm_commit` приймає 5 аргументів.
2. Увійти власником → створити клієнта формою → `select action,source,section,summary,revision from crm_history order by at desc limit 3;` → очікувано: `create / Форма / clients` (плюс проєкт-подія окремо або разом залежно від дії).
3. Швидке подвійне збереження (дубль запиту) → **одна** подія; `select count(*) from crm_history where request_id=...` = 1.
4. Завершити проєкт → одна подія `complete`, `jsonb_array_length(changes)=2`.
5. Змінити курси → `settings`-подія з allowlist-полями; переконатися, що `meta`-оновлення (lastSavedAt) подій НЕ створює.
6. Скасувати завершення з вкладки → нова подія `undo` з `undone_event_id`; на оригіналі `undone_by`; ревізія +1; проєкт у `projectsActive` (виклик `crm_history_undo(event, request, revision, source)` — без патча).
7. Повторне «Скасувати зміну» (новий запит) → відмова «вже скасовано»; повторний confirm того самого підтвердження → без другої події.
8. Між переглядом і підтвердженням змінити дані (інша вкладка) → `CRM_CONFLICT` / конфлікт у UI, без запису.
9. Імпорт JSON → подія `import` з counts, без кнопки скасування; `undone_event_id`/`undone_by` не порожні лише для справжніх пар undo.
10. Ліміти: `update crm_history set at = now() - interval '100 days' where id in (select id from crm_history where owner_id=auth.uid() order by at desc offset 5);` → list → найстаріші видалені, **пара undone (якщо є) збережена разом**.
11. Анонім/інший користувач: `select * from public.crm_history;` і `POST /rest/v1/rpc/crm_history_list` публічним ключем аноніма → відмова; для іншого зареєстрованого власника (якщо створено) — порожній список, не чужі події.

2. **`jsonb_typeof` проти JSON-вузла (P1.2):** валідація ID у `crm_commit`/`crm_history_undo` використовує `e->'id'` (текстове `e->>'id'` лише для trim). Покрито випадки: число, відсутній, JSON-null, порожній рядок, дублікати, не-масив.
3. **Cleanup (P1.3):** внутрішня `ranked` містить `at` — запит очищення виконується; перевірено на порожньому/одній/застарілих подіях і захищених undo-парах (SQL-тест).
4. **Неоднозначне `k` (P1.4):** `crm_apply_collections` і всі цикли використовують `t.k`/окремі імені змінних; переглянуто всі функції на колізії змінних і колонок.
5. **Формат patch (P1.5):** `crm_history_undo` більше НЕ приймає клієнтський патч (`p_patch` прибрано з сигнатури). Клієт (`SupabaseDataSource.historyUndo`) передає лише `(event, request, expected_revision, source)`; контракт-тест фіксує відсутність `p_patch`.
6. **Унікальність фінального стану (P1.6):** перевірка активні/завершені ведеться за ФІНАЛЬНИМИ колекціями (patch або БД) — коректне переміщення (undo завершення) проходить; реальний дубль відхиляється (SQL-тест).
7. **Серверна інверсія та ревізія (P1.7):** сервер сам обчислює інверсію `ev.changes` з актуального стану під блокуванням; `p_expected_revision` обов'язковий (`null` → `CRM_INVALID_REQUEST`); невідповідність «після» → `CRM_UNDO_CHANGED` без перезапису; обхід залежностей → `CRM_UNDO_DEPENDENCY`; bulk/import/undo — `CRM_UNDO_NOT_ALLOWED`; ідемпотентність прив'язана до (request, подія). Сторонній «неінверсний патч» більше неможливий за конструкцією.
8. **Локальна чесність rollback:** верифіковане відкочування; стійкий інцидент `crm_undo_incomplete_v1` (блок + issue, переживає перезапуск); мітка до записів даних; `notify` про збій журналу (тести `history.test.ts`).

## Ревізія 3: виправлення другого огляду (P1/P2)

1. **Типи посилань у undo (P1):** «Відновлювані поля-посилання» порівнювали `x->>'id' = v_field->'before'` (text = jsonb → 42883). Тепер `v_field->>'before'` (text=text) для clientId/developerId/partnerId/projectId. Регресія в SQL-тесті: undo зміни `clientId` A→B працює; після видалення A — `CRM_UNDO_DEPENDENCY` без змін records/revision/журналу.
2. **Наявність поля окремо від значення (P1):** diff (`crm_history_diff_collection`/`_settings`) пакує `beforeExists`/`afterExists` (SQL NULL від `->` = відсутній ключ ≠ JSON-null). Undo перевіряє «після» з урахуванням наявності; відсутнє «до» **прибирає ключ** (`#-`), а не пише null. Події **без прапорців (старий формат) не скасовуються** (`CRM_UNDO_NOT_ALLOWED`) — чесна відмова замість вгадування; у production старих подій немає (міграція не застосована). TS-engine/`normalizeHistoryEvent` підтримують прапорці; старі TS-події трактуються за наявністю ключа в JSON (узгоджено з `deepEqual`). UI/експорт: відсутність показується як «—», без «null»-бруду. SQL-тести: значення→відсутність, відсутність→значення (undo прибирає ключ), значення→явний null, null→значення, відсутній `usdtRate` (порівняння ПОВНОГО стану налаштувань); TS-тести: ті самі правила на engine + локальний E2E (ключ прибрано, не null).
3. **False-pass helper (P1):** `expectSqlError` переписано: запит і catch без assert; окремі `assert.ok` після; самоперевірки в тесті (успішний запит → відмова перевірки; чужа помилка → відмова перевірки). Усі негативні SQL-сценарії (доступ, ревізія, типи ID, залежності, повтори, bulk) повторено під виправленим helper.
4. **Відтворюваний SQL-прогін (P2):** `@electric-sql/pglite` **0.5.9` закріплено як devDependency (package.json + lock); `npm ci` відтворює середовище. Тест більше НЕ пропускається без runtime (assert замість skip). Додано **`npm run test:sql`** (`scripts/run-sql-tests.mjs`): фокус-гейт, що завершується помилкою (exit 1), якщо pglite відсутній — приймання/реліз не повинні приймати skip як PASS. Тимчасова БД/секрети не комітуються (PGlite працює в пам'яті).

## Залишкове зауваження: локальний engine (null ≠ відсутність)

У `computeUndoPlan` обидві гілки (оновлення запису та налаштувань) прирівнювали
`null` до відсутності ключа (`currentValue === undefined || currentValue === null`)
для `afterExists=false`. Це суперечило новим прапорцям наявності й серверній
перевірці (SQL `->` розрізняє відсутній ключ і JSON-null): подія прибрала поле,
а пізніше його встановили в `null` — локальний engine дозволяв undo і затирав
пізнішу зміну, тоді як сервер відмовляє (`CRM_UNDO_CHANGED`), і remote preview
не відповідав SQL.

Виправлення (`lib/history/engine.ts`): наявність ключа визначається через
власну властивість із відмінним від `undefined` значенням (`hasOwnKey`) —
`afterExists=false` вимагає відсутності ключа (явний `null` → конфлікт);
`afterExists=true` вимагає присутності ключа та збігу значення. `undefined`
≈ відсутній (JSON-семантика, як і раніше), `null` — лише явне значення.
Той самий engine живе в `store.previewUndo`, тож **remote preview тепер
відповідає серверній відмові** для тієї ж події/стану.

Регресії: запис і налаштування (подія прибрала поле → поточний `null` →
конфлікт, без перезапису); позитиви «відсутній→відсутній» і «null→null»;
локальний E2E — конфлікт лишає дані, журнал і позначку `undoneBy` незмінними.

## Гарантії локального режиму (фактичні)

- Подія додається **після успіху** дії одним `setItem`; часткового підриву JSON ключа не буває.
- Збій запису журналу: дані збережені; recovery-мітка + видимий issue; наступне читання дописує подію. Якщо й мітку записати не вдалося — подія втрачається, але зміна без скасування видима в журналі-прогалині (не ховається під виглядом повного журналу).
- Атомарності між кількома колекціями/журналом у localStorage немає (як і раніше): невдала доменна дія може лишити частковий стан **без** події — це видимий інцидент/блокування, а не прихований розклад.
- Локальний undo (ревізія 2): **стійка мітка `crm_undo_incomplete_v1` пишеться ДО першого запису даних** і знімається лише після повного успіху; переривання/збій не лишає приховано змішаного стану — мітка переживає перезапуск і **блокує записи** до перевірки (видимий issue + `writeBlockedReason`). Відкочування після збою **верифікується повторним читанням**: лише підтверджений вікат дозволяє стверджувати «відкочено»; непідтверджений → чесне повідомлення «стан непевний — перевір/віднови з копії». Якщо дані відновлено, а подію журналу дописати не вдалося — повторне скасування блокує перевірка стану (не буде подвійного відновлення). Збій запису події після успішної дії сповіщає підписників (`notify`) — issue видимий в UI одразу.

## Залишкові обмеження
