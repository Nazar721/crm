## Архітектура (коротко)

Журнал — **окремий шар від DataSnapshot**: він не входить у snapshot, не потрапляє в експорт даних і в AI-контекст як повні дані (лише короткі підсумки). Подія описує **фактичну різницю даних групи**: один commit = одна група = одна кнопка скасування.

- **Remote:** подія створюється **всередині транзакції `crm_commit`** з фактичного diff старого та нового стану колекцій/налаштувань. Успішний commit і журнал атомарні; повтор того самого `request ID` не створює нової події (перевірка `last_request` до diff). **`crm_history_undo`** — окрема серверна транзакція: перевірка власника, ідемпотентність за `request ID`, **звірка ревізії під `FOR UPDATE`**, застосування патчу (тільки зачеплені колекції + allowlist налаштувань) і вставка події-відновлення разом із позначкою `undone_by` на оригіналі. Стара подія ніколи не видаляється.
- **Local:** після **успіху** доменної дії (`atomicAction`) різниця до/після перетворюється на подію тим самим TS-engine (`lib/history/engine.ts`). Подія пишеться **одним `setItem`** в окремий ключ із **recovery-міткою** `crm_history_pending_v1`: збій запису лишає видимий issue + мітку, наступне читання дописує подію. Атомарності між даними та журналом у localStorage немає — і це задокументовано, не приховано.
- **Скасування:** спільний TS-engine (`computeUndoPlan`) перевіряє поточні значення проти очікуваного «після» події, залежності (клієнт←проєкти, фахівець/партнер←проєкти, проєкт←транзакції), унікальність ID проєктів між активними/завершеними та валідність посилань відновлюваних записів. Група застосовується **атомарно або не застосовується    взагалі**; непов’язані пізніші зміни зберігаються. Повторне скасування тієї самої події → відмова `already_undone`; повтор того самого `request ID` → ідемпотентний успіх без другої події.

## Що зроблено для користувача

- **Налаштування → Історія змін** (нова вкладка): дата/час, розділ, дія, джерело (Форма/Помічник/Імпорт/Система/Застасунок), запис, опис; фільтри за розділом/дією/періодом; пагінація (20/сторінка); розкриття рядка — деталі «було → стало»; кнопка **«Скасувати зміну»** → **попередній перегляд відновлення** (що саме буде відновлено) → явне підтвердження. Після успіху створюється нова подія відновлення (бейдж «скасовано» на старій).
- Події **Імпорт/Відновлення** показуються без кнопки скасування і з посиланням «Відновити з копії» (вкладка «Копії та імпорт»).
- **Експорт/імпорт історії** (окремий JSON, не частина резервної копії даних). Імпортована історія — **окремий недовірий блок лише для перегляду**: без права скасування, з бейджем «імпортована», з вилученням секретів.
- Межа історії в UI: «починається після встановлення пакета; останні 90 днів / до 2000 груп; за межами — скасування недоступне».
- AI: отримує короткі підсумки журналу (`history` у контексті, ≤40 подій), може пояснювати зміни і готувати чернетку скасування (`domain:"history", action:"update", recordId`); маршрут показує попередній перегляд і відмовляє при конфлікті/недоступності. Підтвердження виконується через доменну дію з джерелом «Помічник». Модель не може редагувати журнал і не визначає автора (джерело — лише інформаційний атрибут; власника перевіряє сервер).

## Міграція: `supabase/003-history.sql`

- **Порядок:** `SETUP.sql` (або 001+002) → **`003-history.sql`**. Застосувати **до публікації клієнта пакета 03** (клієнт без міграції працює у деградованому режимі: дані без журналу, вкладка історії показує підказку).
- Старий клієнт **сумісний**: виклики `crm_commit(3 арг.)` ідуть через нову функцію з типовим `p_source = null` → **«Застасунок»**.
- Що створюється: таблиця `crm_history` (RLS увімкнено, **без grant до anon/authenticated** — доступ лише через SECURITY DEFINER функції з перевіркою `auth.uid()`+`crm_owners`); хелпери diff/label/summary/bulk/cleanup/apply (усі з `revoke ... from public, anon, authenticated`); оновлений `crm_commit`; `crm_history_list/get/undo`.
- Обмеження: 90 днів / 2000 подій; очищення **захищає живі recovery-посилання** (подія, на яку посилається утримуване відновлення, не видаляється — пара лишається цілісною; захист має пріоритет над суворим капом).
- Відкат: `drop function ...; drop table public.crm_history;` — на дані не впливає (крім `crm_commit` — треба повернути 3-аргументну версію з `001-crm.sql`).

## Що НЕ перевірено (чесно)

- **Реальний SQL не виконувався**: на цій машині немає Postgres/Docker/supabase CLI. Fake-RPC тести — лише контракт клієнта. Поведінку `003-history.sql` (diff, undo, ліміти, RLS) мусить перевірити **основний агент на контрольованій БД** — сценарії нижче.
- Реальний браузер/iPhone, живий AI-провайдер, production-база — не виконувались.
- Responsive/JS UI вкладки історії — статична перевірка (typecheck/lint/build), без browser-run.

## Репродукції для основного агента (контрольована БД)

1. Застосувати `003-history.sql`; перевірити `select proname from pg_proc where pronamespace='public'::regnamespace and proname like 'crm_history%';` (має бути list/get/undo + хелпери) і що `crm_commit` приймає 5 аргументів.
2. Увійти власником → створити клієнта формою → `select action,source,section,summary,revision from crm_history order by at desc limit 3;` → очікувано: `create / Форма / clients` (плюс проєкт-подія окремо або разом залежно від дії).
3. Швидке подвійне збереження (дубль запиту) → **одна** подія; `select count(*) from crm_history where request_id=...` = 1.
4. Завершити проєкт → одна подія `complete`, `jsonb_array_length(changes)=2`.
5. Змінити курси → `settings`-подія з allowlist-полями; переконатися, що `meta`-оновлення (lastSavedAt) подій НЕ створює.
6. Скасувати завершення з вкладки → нова подія `undo` з `undone_event_id`; на оригіналі `undone_by`; ревізія +1; проєкт у `projectsActive`.
7. Повторне «Скасувати зміну» (новий запит) → відмова «вже скасовано»; повторний confirm того самого підтвердження → без другої події.
8. Між переглядом і підтвердженням змінити дані (інша вкладка) → `CRM_CONFLICT` / конфлікт у UI, без запису.
9. Імпорт JSON → подія `import` з counts, без кнопки скасування; `undone_event_id`/`undone_by` не порожні лише для справжніх пар undo.
10. Ліміти: `update crm_history set at = now() - interval '100 days' where id in (select id from crm_history where owner_id=auth.uid() order by at desc offset 5);` → list → найстаріші видалені, **пара undone (якщо є) збережена разом**.
11. Анонім/інший користувач: `select * from public.crm_history;` і `POST /rest/v1/rpc/crm_history_list` публічним ключем аноніма → відмова; для іншого зареєстрованого власника (якщо створено) — порожній список, не чужі події.
12. Стара сигнатура: виклик `select public.crm_commit(0, gen_random_uuid(), '<поточний snapshot jsonb>');` (з роллю власника) → працює, `source='Застасунок'`.
13. AI (з налаштованим провайдером): «покажи останні зміни» → підсумки; «скасуй останню зміну» → чернетка з попереднім переглядом; підтвердження → подія `undo` з джерелом «Помічник»; демо-режим запису не робить.

## Гарантії локального режиму (фактичні)

- Подія додається **після успіху** дії одним `setItem`; часткового підриву JSON ключа не буває.
- Збій запису журналу: дані збережені; recovery-мітка + видимий issue; наступне читання дописує подію. Якщо й мітку записати не вдалося — подія втрачається, але зміна без скасування видима в журналі-прогалині (не ховається під виглядом повного журналу).
- Атомарності між кількома колекціями/журналом у localStorage немає (як і раніше): невдала доменна дія може лишити частковий стан **без** події — це видимий інцидент/блокування, а не прихований розклад.
- Локальний undo: послідовний запис із відкочуванням уже записаних колекцій при збої; якщо дані відновлено, а подію журналу дописати не вдалося — повторне скасування блокує перевірка стану (не буде подвійного відновлення).

## Залишкові обмеження

- Історія починається з моменту застосування пакета; старішої немає і не вигадується.
- Події-відновлення не скасовуються (немає «повторення» undo) — навмисно для першої версії.
- Групи >50 змін або >96 КБ JSON (та весь імпорт) зберігаються як підсумок — без деталей і без скасування.
- Скасування між пристроями захищене ревізією (будь-яка паралельна зміна → конфлікт до повторного перегляду), а не тільки зміною зачеплених полів.
- Контекст моделі містить лише ≤40 коротких підсумків; повний JSON імпорту в журнал і контекст не потрапляє.
- `ASSISTANT-INSTRUCTIONS.md` (документ) не оновлювався під новий розділ промпту — чинний промпт у `lib/assistant/instructions.ts`.
