## Перенесення

Після встановлення SQL і входу у CRM потрібно перевірити читання порожньої бази, створення синтетичного запису, його видалення, доступ іншого користувача та конфлікт двох пристроїв. Лише після цього завантажити фінальний JSON через «Налаштування → Імпорт», звірити попередній перегляд і підтвердити атомарне перенесення. Під час перенесення не додавати записи до старої CRM; якщо після експорту працювали з даними, потрібен новий фінальний експорт.

Попередня перевірка файлу від 06.10: 666 записів, їхні поля, ID та зв'язки збережено без змін. 5 історичних фінансових записів не мають рахунку; вони зберігаються без автоматичного призначення рахунку. Наявні посилання на відсутніх фахівців та один проєкт залишаються без змін. Докладні числові результати — MIGRATION-CHECK.json. Це звірка підготовки; не підтвердження фактичного перенесення у хмару.

## Реалізація та межі перевірки

crm_records містить окремі записи зі старим текстовим ID, категорією, порядком і повним JSON payload. crm_state зберігає налаштування/метадані та версію. crm_commit перевіряє версію, блокує рядок стану й записує всю дію однією транзакцією, змінюючи лише відмінні записи. Застаріла версія не перезаписує новішу. Створення клієнта з проєктом і завершення проєкту виконуються атомарно. Неоднозначний мережевий збій блокує повторні записи до оновлення сторінки й перевірки стану; автоматичного повтору створення немає.

RLS і закриті функції перевіряють authenticated user та crm_owners. Читання неавторизованого акаунта не дозволене, прямі зміни таблиць заборонені клієнтським ролям. Ключі провайдерів у цих таблицях не зберігаються. AI та голос підключаються окремим наступним кроком.

74 автоматизовані перевірки та build виконані локально. SQL додатково виконано у локальному PostgreSQL (PGlite): усі 666 записів повернулися без змін; конфлікт версій, прямий запис, сторонній акаунт і анонімний доступ перевірено. Це не звернення до хмарної бази. Реальний Supabase, вхід на ноутбуці/iPhone та продуктивність у браузері ще потребують перевірки. Обидва пристрої читають одну базу, але автоматичне realtime-оновлення списків поки не додано — для отримання нових змін іншого пристрою оновити сторінку. Захист від перезапису застарілих даних уже діє.
